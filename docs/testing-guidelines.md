# テスト方針

このアプリのテストをどの粒度でどう書くか、という判断基準をまとめる。

## このアプリのテストが難しい根本理由

このアプリは「2週に1回以上」という高頻度でゲーム側のバランス調整パッチが入る計算機である。つまり、
**実験体の基礎値・スキル係数などの「データ」は非常に頻繁に変わるが、それらを合成する「アルゴリズム」自体は
めったに変わらない**。

テストを設計するときは、常に次を自問する。

> このテストは、コードを一切変更していなくても、ゲームバランスパッチだけで落ちうるか？

落ちうるなら、それは「データの正しさ」と「ロジックの正しさ」を混同したテストになっている可能性が高い。
実際、既存の`src/test/*-tooltip.test.tsx`（全実験体・全装備・全武器スキルのツールチップをレンダリングして
スナップショット照合する）は、2026-08-29時点で873件中870件が失敗する状態だった。原因はコードの不具合では
なく、ゲームデータの変化やレンダリング内容の変化にスナップショットが追従できていないことによるもので、
「今何かが壊れているのか」を判別する材料として機能していない。

## 層ごとの方針

| 層 | 対象 | テストに使うデータ | パッチ耐性 |
|---|---|---|---|
| ① ロジック層 | `calculation.ts`・`combine-components.ts`・`extractMultiplier`・`createMitigation`等の純粋関数 | **自作の合成値**（実データ不使用） | 高 |
| ② Pure View | `*.view.tsx`（Storeに依存しない、props→JSXのコンポーネント） | 自作のprops | 高 |
| ③ Container | Store接続層（`useSubjectStateStore`を呼ぶコンポーネント） | 自作のStore状態（実キャラ辞書は使わない） | 高 |
| ④ 実データ全量スナップショット | 実際の全実験体・全装備を対象にした`toMatchSnapshot()` | 実データ全量 | **低** |

### ① ロジック層 — 最優先で厚くする

`app-types/**`配下の純粋関数（Reactに依存しない）は、実在するどの実験体のデータにも依存しない自作の
数値でテストする。「このアルゴリズムが、想定した入力に対して想定した計算をするか」だけを検証すればよく、
パッチの影響を一切受けない。

例: `src/test/extract-multiplier.test.ts`（`components/damage/damage-table-util.ts`の`extractMultiplier`）。
固定倍率・スキルレベル依存配列・ラベル付き複数要素の合成規則を、自作の数値だけで検証している。

このアプリの計算コアの全体像は[CLAUDE.md](../CLAUDE.md)の「計算コア」節、合成順序の詳細は
[ステータスモデル](./status-model.md)の「要素の合成順序」を参照。

### ② Pure View — 「propsを渡したらどう振る舞うか」を検証する

`features/*/components/*.view.tsx`はStoreに一切依存しないため、React Testing Library (RTL) で
自作のpropsを渡してレンダリングし、表示内容やイベントハンドラの呼び出しを検証できる。ゲームデータを
一切用意する必要がない。

例: `src/test/slider-section.test.tsx`（`features/subject-config/components/slider-section.view.tsx`）。
このテストを書く過程で、実際に本番のバグを1件発見した——マウント時に`props.value`（現在値）を無視して
常に最大値から表示を始め、デバウンス経由で永続化済みの値を黙って最大値に上書きしてしまう不具合
（`git log`でこのファイルの修正コミットを参照）。**スナップショットテストでは検出できず、
「このpropsを渡したら何が起きるべきか」を明示的にアサートする振る舞いテストだからこそ検出できた**
好例として残している。

留意点:
- `useDebounce`のような時間依存の処理は`vi.useFakeTimers()` + `vi.advanceTimersByTime()`で決定的にする。
  実時間の`setTimeout`待ちでテストを書かない。
- `<input type="range">`のようなネイティブ要素の値は、jsdom上では文字列として保持される
  （`toHaveValue("30")`であって`toHaveValue(30)`ではない）。

### ③ Container — Store接続の配線を検証する

`features/*/containers/*.tsx`は`useSubjectStateStore`を呼ぶため、`SubjectConfigStoreContext.Provider`
（`features/subject-config/store.tsx`）でラップする必要がある。ここでも実際の実験体辞書やlocalStorageを
経由させる必要はなく、`createSubjectConfigStore`で作ったstoreインスタンスに対して
`store.setState({...})`で直接テスト用の状態を注入し、「Storeのこの値がpropsのこの値に正しく変換されているか」
だけを検証すればよい。まだこのアプリにこの層のテスト例はないため、今後書く際はこの方針に従う。

### ④ 実データ全量スナップショット — smoke test相当に位置づけを縮小する

既存の`src/test/{item,subject-skill,weapon-skill}-tooltip.test.tsx`は、削除はせず、**役割を
「クラッシュせずレンダリングできること」の確認（smoke test）に縮小する**方針とする。

- 現状の`toMatchSnapshot()`による厳密な内容一致の検証はやめる（パッチのたびに大量に落ち、シグナルとして
  機能しないため）。
- 「特定のスキル・装備の組み合わせでレンダリングが例外を投げないか」を確認する用途には引き続き使える。
- 特定の計算結果の値を厳密に固定したい場合は、④のような実データ全量ではなく、①のロジック層で
  自作の入力値を使ってテストする（層を混同しない）。

## 実装時のチェックリスト

新しくテストを書く・既存テストを直すときは、次の順で検討する。

1. これは純粋なロジック（Reactに依存しない計算）か？ → ①として自作データでテストする。
2. これはStoreに依存しないViewか？ → ②としてRTLで自作propsをテストする。
3. これはStoreに依存するContainerか？ → ③としてStoreへ直接状態を注入してテストする。
4. どうしても実データ全体を対象にしたい（例：新実験体追加時に既存実装が壊れていないか一括確認したい等）か？
   → ④のsmoke testの対象に加えるが、厳密な値の一致は求めない。
